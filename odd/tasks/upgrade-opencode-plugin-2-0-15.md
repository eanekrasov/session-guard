# Upgrade `@opencode/plugin` to 2.0.15

## Objective

Pin `@opencode/plugin` to the exact published version `2.0.15` and verify that
the project's current V2 adapter and contract remain compatible with the
installed package.

## Problem

The dependency currently declares the moving `beta` tag and resolves to
`0.0.0-beta-19398`. That is not a reproducible dependency contract and does
not satisfy the requested V2 package baseline.

## Why

An exact dependency declaration and lock resolution make the host API baseline
reproducible. The V2 adapter relies on host-facing APIs, so the upgrade must
also establish whether the installed V2 surface remains compatible without
speculative implementation changes.

## Scope

- Update only `@opencode/plugin` to exact version `2.0.15` through Bun.
- Let Bun update the corresponding `bun.lock` resolution.
- Inspect the installed declarations and the project's V2 adapter/contract for
  `Plugin.define`, `Context`, tool hooks and transforms, session access, event
  subscription, cleanup, and registration disposal.
- Run the required focused, repository, build, and safe host-smoke checks.

## Constraints

- Do not manually edit `bun.lock`.
- Do not update unrelated dependencies or absorb other agents' changes.
- Do not broaden scope into V2 adapter implementation if a compatibility break
  is found; document the exact incompatibility and stop as partial.
- Do not publish, push, or open a pull request.
- Keep technical artifacts in English.

## Acceptance Criteria

1. `package.json` declares `@opencode/plugin` as exactly `2.0.15`.
2. `bun.lock` is generated by Bun and resolves that package to exactly `2.0.15`.
3. The installed package state is verified, rather than inferred from the
   manifest or lockfile alone.
4. Every listed V2 surface used by the project is compared with installed
   declarations; exact incompatibilities, if any, are documented without
   implementation changes.
5. Required checks have recorded outcomes, including an honest smoke result.
6. One conventional commit contains only the dependency update, generated lock
   change, this ODD record, and necessary compatibility documentation.

## Forecast

The dependency declaration and lock resolution are expected to change. The
highest-risk uncertainty is a V2 declaration mismatch, especially around host
registration lifecycle and tool/event APIs. If such a mismatch is observed,
the work unit will preserve the dependency update only when its checks remain
runnable, document the break precisely, and request a separate implementation
decision.

## Progress

Baseline recorded: the manifest declared `beta`; `bun.lock` and installed
`node_modules/@opencode/plugin/package.json` resolved it to
`0.0.0-beta-19398`. npm metadata confirmed that `@opencode/plugin@2.0.15`
exists.

Resolution completed with `bun add @opencode/plugin@2.0.15`; Bun changed only
the manifest declaration and the generated lock entries. The installed package
reports version `2.0.15`; `bun.lock` declares and resolves the same exact
version. Its coupled OpenCode packages (`@opencode/ai`, `client`, `protocol`,
`schema`, and `util`) resolved from `0.0.0-beta-19398` to `2.0.15` as the
package's own exact dependency graph. No manual lock edit occurred.

Installed declaration comparison found no incompatibility in the V2 surfaces
used by this project:

- `Plugin.define({ id, setup })` and `Cleanup` are exported by
  `@opencode/plugin/promise/plugin` and match `src/index.ts`.
- `Context` exposes `location`, `tool`, `session`, and `event`; the adapter's
  project/worktree reads match `Location.Info`.
- `ctx.tool.hook` exposes `execute.before` and `execute.after` event unions
  matching the adapter's identity and completion/error mapping.
- `ctx.tool.transform` accepts a `ToolEditor` and returns a disposable
  `Registration`, matching workflow-list registration.
- `ctx.session.get` and `ctx.event.subscribe` are present. The former is used
  by the parent resolver; the latter remains deliberately deferred.
- `Registration.dispose(): Promise<void>` and setup cleanup match the adapter's
  reverse-order, idempotent disposal behavior.
