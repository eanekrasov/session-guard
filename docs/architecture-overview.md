# Как это устроено

Документ для того, кто **работает под управлением плагина**, но собственных
профилей не пишет: что происходит с вашей сессией, кто и почему вас
останавливает, и где смотреть состояние.

Если вы собираетесь писать профиль — вам нужен
[profile-authoring.md](profile-authoring.md).

---

## Зачем это

Агент, которому дали инструменты, способен пройти весь путь одним рывком:
написать код, объявить его проверенным и закоммитить. Проверял он при этом сам
себя.

Плагин ставит между шагами машину состояний. Она не делает работу и не судит о
её качестве — она следит, чтобы **порядок соблюдался и доказательства
собирались**: план утверждён до правок, работа проверена до коммита, а
коммит несёт ровно то, что было проверено.

---

## Три вещи, из которых всё состоит

**Профиль** — что именно вы делаете. Каталог со схемой workflow, промптами
агентов и правилами проверки файлов. В поставке их три: `base` (общий),
`android`, `harness`.

**Схема** — машина состояний: стадии, переходы между ними и условия. Профиль
может держать несколько схем, сессия выполняет ровно одну.

**Сессия** — ваш конкретный прогон: где вы сейчас, что уже проверено, какие
задачи в работе, что менялось на диске. Файл, который живёт между вызовами.

---

## Что происходит с сессией

```
workflow-create → стадия planning
      │
      │  оператор утверждает план (consent)
      ▼
  tasks_ready → execution ──┐
                  │         │  цикл по задачам:
                  │         │  code → verify → задача завершена
                  └─────────┘
      │  все задачи завершены
      ▼
  validation → commit → done
```

Двигают сессию не агенты, а **переходы**: у каждого ребра есть условие, и пока
оно ложно, ребро закрыто. Соседство двух стадий в схеме само по себе не значит,
что перейти можно.

---

## Словарь

**Стадия** — где сессия сейчас. Стадия решает, кто на ней может работать и что
именно там разрешено делать.

**Гейт** — проверка, которой стадия ждёт: `review`, `qa`, свои. Гейт закрывает
агент, отчитываясь о своей работе.

**Вердикт ядра** (`checks`) — то, что движок вынес о вашем ходе, **посмотрев на
диск**: упал ли инструмент, писали ли вы за пределами разрешённой области,
прошли ли проверки файлов. Это не гейт: гейт агент может выставить себе сам, а
этот вердикт — нет. В том и смысл.

**Согласие** (consent) — решение оператора, которого ждёт переход. У согласия
есть имя: `plan`, `deploy`, любое, какое назначила схема. Вам показывают
описание и файлы, вы выбираете grant или decline.

**Задача** — отдельная единица работы со своим набором файлов, которые ей
разрешено менять. Проходит статусы `pending`, `running`, `completed`, `failed`,
`cancelled`.

**Бюджет повторов** — сколько раз задача может вернуться на доработку, прежде
чем решение передадут оператору.

---

## Почему вас останавливают

Отказ всегда называет причину. Виды такие.

**Действие не объявлено на стадии.**

```
Refused: 'edit' is declared on this stage, but its condition does not hold:
session.approved('plan')
```

Стадия перечисляет, что на ней можно. Если списка нет — можно всё; если есть —
он исчерпывающий. Правки до утверждённого плана обычно запрещены именно так.

**Файл вне области записи задачи.**

```
write refused: 'src/other.ts' is outside every active task's writeScope
(task-0: [src/auth/**])
```

У задачи объявлен набор файлов. Отдельный случай: **задача без объявленной
области — только для чтения**, и тогда отказывается любая запись.

**Агент не тот.**

```
Agent reviewer is not allowed in stage code. Allowed: coder, orchestrator
```

Стадия называет своих исполнителей. Отдельно: менять состояние задач
(`workflow-tasks-set`, `-set-status`, `-resolve-decision`) может только
оркестратор — иначе исполнитель закрывал бы собственную работу без
доказательств. Читать (`workflow-tasks-get`) можно всем.

**Переход закрыт.** Не отказ инструмента, а неподвижность: ждут гейта,
согласия или незавершённых задач. Смотрите гейты, одобрения и задачи — в этом
порядке.

**Коммит не совпал с обещанным.** Перед доставкой ядро выдаёт permit со списком
ожидаемых файлов, а после — сверяет с тем, что реально ушло в HEAD. Коммит,
захвативший лишний файл, расписки не получает.

---

## Коммит

Коммит — не переход, а действие стадии, помеченное `delivers: true`. Порядок
такой:

1. до вызова ядро запоминает HEAD и список файлов, которых ждёт (permit);
2. команда выполняется;
3. после ядро сравнивает новый коммит с ожиданием;
4. совпало — пишется расписка (`deliveryReceipt`), нет — расписки не будет.

Прямой `git commit` и `git push` по умолчанию запрещены: доставка идёт
объявленной командой, чтобы её можно было сверить.

---

## Конец работы

Workflow заканчивается на стадии, из которой схема никуда не ведёт — в базовом
профиле это `done` и `failed`.

Дойдя туда, сессия **уезжает из рантайма в архив**. С этого момента она ничем не
управляет: следующий вызов проходит так, будто workflow нет. Ничего при этом не
теряется — расписка, гейты, вердикты и одобрения остаются целы.

Тогда же записывается, **чем и почему** кончилось: каким переходом, по какому
условию, какие проверки провалились и какие бюджеты были исчерпаны. Без этой
записи «дошли до конца», «провалились» и «застряли» выглядели бы одинаково.

---

## Где смотреть состояние

**Боковая панель TUI** — стадия, гейты, задачи с их вердиктами, бюджеты
повторов, открытые вызовы. Панель подробностей показывает сессию целиком,
включая запись об исходе.

**Dashboard** — то же в браузере, по всем сессиям сразу; читает и рантайм, и
архив.

**Файл сессии** — под каталогом данных opencode, `session-guard/runtime/`.
Законченные лежат в `runtime/archive/`.

## Инструменты, которые вы увидите

| Инструмент                        | Что делает                                  |
| --------------------------------- | ------------------------------------------- |
| `workflow-create`                 | начать workflow по выбранной схеме          |
| `workflow-list`                   | какие профили и схемы доступны              |
| `workflow-consent`                | подготовить запрос согласия оператора       |
| `workflow-tasks-set`              | задать список задач (оркестратор)           |
| `workflow-tasks-get`              | прочитать список задач                      |
| `workflow-tasks-set-status`       | сменить статус задачи (оркестратор)         |
| `workflow-tasks-resolve-decision` | решить судьбу задачи с исчерпанным бюджетом |

## Как оно встроено

Плагин подключается к opencode как обычный плагин и вешается на жизненный цикл
вызова инструмента: **до** вызова — допуск, **после** — вердикт и переходы.

До вызова по порядку: guardrails, правила проекта, разбор согласия, допуск
задачи, проверка области записи, действия стадии, permit коммита, начало хода
мутации. После: снятие диффа, проверка инвариантов, запись вердикта, разбор
`<workflow-result>` от агента и попытка применить переход.

Работу делают агенты профиля; плагин их не заменяет. Он решает, **кому** и
**что** сейчас можно, и записывает, **что из этого вышло**.

---

## Если застряли

1. Посмотрите гейты: какой не закрыт.
2. Посмотрите одобрения: не ждёт ли переход согласия.
3. Посмотрите задачи: нет ли незавершённых или ждущих решения оператора.
4. Прочитайте текст отказа целиком — он называет и правило, и условие.

Подробнее — [troubleshooting.md](troubleshooting.md).
