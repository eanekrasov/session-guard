## Facts that were expensive to establish — do not re-derive

**Platform source is at `~/Projects/harness/extra/opencode`**, branch `dev`,
version 1.18.29 — the same as the installed binary. Use it instead of guessing
at host behaviour.

**Throwing in `tool.execute.before` does cancel the tool call.** The host runs
hooks as `yield* Effect.promise(async () => fn(input, output))`
(`packages/opencode/src/plugin/index.ts:294`) and only then reaches
`yield* item.execute(args, ctx)` (`session/tools.ts:111`). A rejected hook is a
defect, so `execute` is never reached. The rejection surfaces through
`failToolCall` (`session/processor.ts:185`) as an errored tool part carrying the
message — the agent reads the reason. Mutating `output.args` does **not** cancel
anything; it only rewrites the arguments the tool receives.

**`permission.ask` is a dead hook.** Declared in `packages/plugin/src/index.ts:261`
and listed in the host's own docs, but `plugin.trigger("permission.ask", ...)`
appears nowhere in `packages/opencode/src`. It is not an available deny channel.

**Agent names carry a profile prefix.** OpenCode scans `{agent,agents}/**/*.md`
and derives the name from the path under that prefix
(`config/agent.ts:13`, `config/entry-name.ts`). `syncProfileAgents` writes into
`.opencode/agents/<profileId>/`, so `code.md` registers as `<profileId>/code`.

**`OPENCODE_AGENT_ID` / `AGENT_ID` are never set by the host.** Verified by
grep over the whole platform source.

## Open — ordered by importance

### Enforcement

1. ~~**`handleCommitTaskAfter` does not enforce `expectedFiles`.**~~ **Fixed.**
   The receipt is now written only when the commit holds exactly the expected
   file set. A mismatch, or a file list git cannot produce, drops the permit,
   writes no receipt, and appends `[workflow-commit-rejected]` to the tool
   output, so the workflow stays in `commit` and the step must be re-run under
   a fresh permit. Covered by `test/app/commit-receipt.test.ts` (5 tests) —
   the first tests to drive `handleCommitTaskAfter` at all.

2. ~~**`workflow.tasks-set-status` is exposed to the agent**~~ **Fixed.**
   `tasks-set`, `tasks-set-status` and `tasks-resolve-decision` are now refused
   unless the calling agent (`ToolContext.agent`, which the host does populate)
   is in the schema's `taskControlAgents`, default `['orchestrator']`; an
   unnamed caller is refused too. `tasks-get` stays open. Covered by
   `test/app/task-control.test.ts` (9 tests).

3. **`checkTransition` without a session is fail-open** (`src/domain/engine.ts`).
   Guard, consent and gates are all skipped when `session` is undefined, and the
   result is `allowed: true`.

### Concurrency

4. ~~**`SessionQueue.executeInline` loses the reentrant write.**~~ **Fixed.**
   Caught live by the host smoke run: `workflow.tasks-set` reported
   "Stored 1 task(s)" while the persisted session held none. The inner
   `enqueue` reloaded the session and saved it; the outer save then wrote its
   stale copy over the top. A reentrant call now runs on the session the outer
   execution already holds.

5. ~~**Reentrancy is detected by a global `Set` keyed on root id.**~~ **Fixed.**
   Reentrancy is now decided by async call context (`AsyncLocalStorage`), so a
   concurrent top-level `enqueue` queues instead of running inline. Both are
   covered by `test/app/session-queue.test.ts`.

6. **No optimistic concurrency in `WorkflowStore.save`** — `revision` is
   incremented but never compared. `queues` map is never cleaned up.

7. **`session.testStatus['parentID']` is written nowhere in `src`** (only in a
   test). So `parentCache` is always identity and `resolveRoot` is a no-op in
   production: serialisation never links a parent to its children. Also, storing
   a parent id inside a test-status record is a smell of its own.
   **Reproduced end to end by the host smoke run:** a dispatched subagent edits
   in its own session, so the parent's `invariants` gate never turns green from
   delegated work — which is all the work this workflow does. `base.yaml`'s
   `code → verify` guard therefore cannot hold for a delegated `code` stage.

### Guard DSL (`src/schema/guard-ast.ts`) — **closed**

Items 8–13 are fixed. The property surface is now an **allowlist** (the
user's call): own data is readable by its own name, a method is reachable only
if it is named in `ALLOWED_METHODS`, and `__proto__` / `prototype` /
`constructor` throw however they are written — a literal key and a dynamic one
go through the same check, so neither reaches further than the other.

| Was | Now |
|---|---|
| `(x) => …` did not parse; the guard silently became `false` | parses, including `(a, b) => …` |
| `obj[expr]` compiled to `property: ''` → always `undefined` | a real computed member node |
| the `?.[expr]` branch was dead and substituted `.at()` | optional computed access |
| `__proto__` / `constructor` reachable; `Function` blocked by accident | refused by name, with an error |
| each arrow body got a fresh budget, so `MAX_EVAL_STEPS` was per-callback | one budget per evaluation |
| every failure was `catch → false`, so a broken guard and a false one looked alike | still fail-closed, but the error is reported through `onError` and logged with the profile id and expression |

`require('./guard-ast.ts')` was already gone — that half of item 13 had been
fixed earlier. Covered by `test/schema/guard-allowlist.test.ts` (20 tests).

### Schema machinery

**25. ~~The shipped base machine cannot reach `commit`.~~ Fixed.** The cause
was two competing models of the same idea — `base.yaml` treated review and qa
as phases closed by `session.gates`, `task-cycles.yaml` as stages closed by a
`<workflow-result>` tag, and nothing joined them. Both are now one concept, the
**stage**, and `base.yaml` runs
`planning → tasks_ready → execution [code → verify] → validation → commit → done`.
A live subagent closing a gate is covered by the `verify-loop` host smoke
scenario. See `docs/stage-model.md` and `docs/stage-model-plan.md`.

This also closed items 14–19 in part: `compileWorkflow` is wired in and
validating, `gateMapping` and the schema-level `verifiers` list are gone into
`gates:` on a stage, and `allowedAgents` has one implementation at both
levels.

**26. NEW — consent was broken end to end.** Two independent defects, both
fixed: `workflow.consent` saved the session between building the manifest and
building the tag, so `session.revision` advanced and the tag's `revision`
attribute never matched its own manifest — `parseConsentRequest` rejected every
tag the plugin itself produced. And `ConsentOrchestrator.after` looked for the
tag in `output.output` (the operator's answer) instead of the question's args.
Either one alone made consent impossible. Covered by
`test/app/consent-roundtrip.test.ts`.


14. **`compileWorkflow` is never called from `src`** — only tests. No phase
    reference validation runs at runtime. This is plan machinery landed in
    `a463ef3` and not yet wired; the same is true of `workflow-model.ts`,
    `run-view.ts`, `scoped-policy.ts`, `resource-claims.ts`,
    `host-call-adapter.ts`, `workflow-module.ts`.
15. `stageLevelGuards` is never populated; `StageDef.exitGuards` (the array form)
    is never read — so `exitGuards: ['allTasksCompleted()']` in
    `task-cycles.yaml` is not enforced.
16. `onFailure` compiles but has no consumer.
17. No profile uses `kind: pass|fail`, so the `requiredGates` branch of
    `checkTransition` is inert.
18. `deriveStageFn` falls back to `'PLANNING'` while stages are lowercase.
19. `editingAgents` and `verifiers` are declarative only — nothing reads them.

### Deferred

20. **`WorkflowStore.load()` returns `null` both when the file is missing and
    when it fails schema validation.** A governed session that stops parsing
    silently leaves the state machine's control. Deferred to release by the
    user's decision (migrations are being ignored during active development).

### Lower priority

21. `workflow-module.ts`: `isDuplicate(genId())` checks a freshly generated id
    and is always false; `validateSnapshot` is an empty placeholder;
    `loadSnapshot` swallows corrupt JSON and returns `null`, silently resetting
    the run.
22. `runtime.ts` dumps raw tool arguments (2000 chars) at `info` level on every
    call — file contents and secrets end up in logs.
23. `guardrails.ts` is a regex blacklist: `\beval\s*\(` and unanchored
    `printenv` fire on ordinary coding output; `git push --force` sits in
    `DATA_EXFILTRATION` at severity `warn`, so it is never blocked.
24. All profile schemas were byte-identical symlinks — now real files, but
    `android/profile.json` still declares `extends: base` **and**
    `schemas: ["android.yaml"]`, which is correct but worth keeping in mind when
    editing.

## Watch out

- **Beware weak tests.** Several existing tests assert nothing
  (`expect(step).toBeTruthy()` on string literals) or set the wrong field while
  their name says the right one. Two such tests were replaced this session. When
  a test passes, check it fails without the fix.
- **`profiles/*/[a-z]*.yaml` were symlinks** to a single file. They are real
  files now, but any future "copy" should be checked with `ls -l`.
- The four schemas resolve through `mergeSchemasToEngineConfig` (per-key,
  last-wins) and `SchemaLoader.mergeSchemas` (whole-field override for
  schema-level `extends:`). Two different merge paths — do not confuse them.
