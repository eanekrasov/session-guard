# Guide: как написать собственную schema

Полное руководство автора профиля, со структурой профиля, наследованием и
примерами — [profile-authoring.md](profile-authoring.md).

## 1. Опишите пользовательский результат

Сначала сформулируйте, чем workflow заканчивается. Затем перечислите только те
фазы, которые пользователь реально должен пройти.

## 2. Опишите фазы

```yaml
stages:
  planning: {}
  execution: {}
  review: {}
  done: {}
```

Названия фаз должны быть понятны пользователю и использоваться одинаково в
переходах.

## 3. Добавьте переходы

Для каждого перехода определите условие, которое можно проверить:

```yaml
transitions:
  - from: execution
    to: review
    guard: "session.gates.invariants == 'passed'"
```

Не добавляйте переход только потому, что две фазы логически соседствуют.

## 4. Добавьте approvals и failure paths

Используйте `consent`, когда пользователь должен явно разрешить переход.
Для неуспешного результата определите `retry` или `terminal` и ограничение
повторов.

## 5. Шаг с коммитом

Коммит — **не переход**. Ребро отвечает на вопрос «можно ли уйти со стадии», а
коммит происходит, оставаясь на ней, и ребром его не выразить. Это действие
стадии, помеченное `delivers: true`.

### Как объявить

```yaml
stages:
  commit:
    actions:
      # доставка
      - action: bash
        commands: ['bun run .*commit-task\.ts.*']
        delivers: true
        guard: "allTasksCompleted('implementation') && session.gates.review == 'passed' && session.gates.qa == 'passed'"

      # осмотреться перед доставкой
      - action: bash
        commands: ['git status', 'git status .*', 'git diff.*', 'git log.*']
  done: {}

transitions:
  - from: commit
    to: done
    guard: 'session.deliveryReceipt != null'
```

Разберём по частям.

**`action: bash`, а не `commit`.** Инструмента `commit` у хоста не существует —
коммит приезжает обычным `bash`. `action` называет **инструмент**, а `delivers`
— **назначение**. Смешивать эти уровни нельзя: раньше в словаре действий был
отдельный `commit`, и он описывал то, чего хост не умеет.

**`commands:` называет вашу команду доставки.** Регулярка якорится и
применяется к каждому сегменту команды. Здесь это `scripts/commit-task.ts` из
поставки, но команда может быть любой — важно, что она объявлена.

**`delivers: true` меняет обработку вызова.** Ядро не входит в жизненный цикл
мутации (доставка не правка), а вместо этого обрамляет вызов проверкой.

**`guard:` — право на коммит.** Условие, при котором доставка вообще разрешена:
вся работа закрыта и все вердикты собраны. Оно намеренно повторяет условие ребра
`validation → commit`: ребро отвечает за движение и перестанет держать, как
только у стадии появится второй вход, — а право на доставку выдаёт действие.

**Вторая запись обязательна.** Объявленный список действий **исчерпывающий**:
без неё `git status` на стадии коммита был бы отказан.

### Что делает ядро вокруг вызова

1. **До вызова** записывается `deliveryPermit`: текущий HEAD и список файлов,
   которые сессия ожидает увидеть в коммите (`changedFiles`, сверенные с HEAD).
2. Команда выполняется.
3. **После вызова** HEAD перечитывается. Только если он действительно сдвинулся
   и коммит несёт ожидаемое, пишется `deliveryReceipt` — SHA коммита.

Поэтому неудавшийся коммит оставляет HEAD на месте, расписки не появляется, и
workflow честно остаётся на стадии `commit`. А коммит, захвативший лишний файл,
расписки не получает: ожидание и факт разошлись.

Расписка — это то, чем вы открываете выход:

```yaml
- from: commit
  to: done
  guard: 'session.deliveryReceipt != null'
```

### Прямой git запрещён по умолчанию

Если стадия **не объявила** `actions:`, ядро применяет свой дефолт: прямой
`git commit` и `git push` отказываются. Это именно дефолт, а не закон — стадия,
объявившая список, отвечает на этот вопрос сама, и `git commit` там отказывается
уже потому, что его в списке нет.

Смысл в том, чтобы доставка шла объявленной командой, которую можно сверить.
Коммит в обход неё сверить не с чем.

### Частые ошибки

- **Забыли вторую запись.** Список исчерпывающий: без неё на стадии коммита
  нельзя даже `git status`.
- **Условие только на ребре.** Ребро пускает на стадию, но не выдаёт права
  коммитить. Право — это `guard:` у записи с `delivers`.
- **Выход открыт не распиской.** Ребро `commit → done` по гейту вместо
  `deliveryReceipt` выпустит сессию из коммита при неудавшемся коммите.
- **Наследование.** `actions` — одно поле стадии, и потомок, объявивший свой
  список, заменяет родительский целиком вместе с записью доставки.

## 6. Подключите schema к profile

Укажите имя schema в `profile.json` через `schemas`, затем проверьте, что профиль
доступен из настроенного каталога профилей.

## 7. Проверьте schema

Проверить нужно не только YAML-синтаксис, но и поведение:

- начальная фаза достижима;
- каждый обязательный переход имеет рабочий guard;
- approval действительно появляется в нужный момент;
- failure path не создаёт бесконечный цикл;
- конечная фаза достижима;
- запрещённые значения отвергаются loader/parser.

## 8. Прогоните пользовательский сценарий

Начните workflow, пройдите happy path, затем отдельно проверьте отказ, ошибку
проверки и повторную попытку. Если поведение отличается от ожидания, сначала
исправьте schema или явно задокументируйте ограничение.
