# Устройство кода

Документ для того, кто **правит сам плагин**: из каких слоёв он состоит, что
чему разрешено знать и где что искать.

Все пути `src/`, `scripts/`, `test/` и `profiles/` ниже относятся к source
repository. Каталоги `<project>/.opencode/**` относятся к целевому проекту и
создаются его OpenCode-конфигурацией или runtime-плагином, а не обязаны быть
частью checkout-а плагина.

Что плагин делает — [architecture-overview.md](architecture-overview.md).
Как подключить — [usage.md](usage.md).

---

## Точка входа

```
src/index.ts        — V1/V2 entrypoints и default с `setup` и `server`
src/public-api.ts   — публичные функции разрешения профиля и чтения сессий
```

`index.ts` вычисляет каталоги профилей и рантайма, создаёт их и отдаёт результат
`createRuntime(ctx, { storeDir, profilesDir })`. Значения передаются **экземпляру**
и никогда не пишутся в `process.env`: запись превращала бы дефолт первого проекта в
глобальный, и второй получал чужие профили.

Сборка source repository выполняется задачей `mise run build` и кладёт три
независимых JavaScript-артефакта: `dist/index.js` (плагин и библиотека),
`dist/cli.js` (команда `sync-agents`) и `dist/tui.js` (боковая панель), а также
две JSON Schema. Скрипт `scripts/verify-build.ts`, вызываемый последним шагом
этой задачи, следит, чтобы артефакты не оказались одним и тем же файлом.

## Слои

```
schema/     чтение и компиляция YAML          ← ничего не знает о сессиях
domain/     правила: движок, допуск, движение  ← чистые функции над состоянием
session/    формат состояния и файловое I/O
app/        рантайм: хуки хоста, оркестрация, ввод-вывод
rules/      правила проекта поверх сообщений
tui/        боковая панель, только чтение
dashboard/  веб-монитор, только чтение
```

Направление зависимостей — сверху вниз. `domain/` не импортирует `app/`;
`schema/` не знает ни о сессии, ни о рантайме. Нарушение этого порядка — первый
признак того, что решение попало не в тот слой.

### `schema/` — что объявил автор профиля

`profile-schema.ts` описывает форму YAML, `schema-loader.ts` читает и сливает
наследование, `compile-workflow.ts` превращает результат в исполняемый контракт и
**отвергает** то, что не сойдётся: неизвестный ключ, недостижимую стадию, стадию
без пути к концу, workflow без конца, гейт вне словаря, не разбираемый guard.
Ошибки компиляции — единственная воронка: у каждой есть путь и имя.

`guard-ast.ts` и `guard-evaluator.ts` — язык условий. Ошибка вычисления даёт
`false`: невычислимое условие не считается выполненным.

### `domain/` — правила

Чистые функции и классы, работающие над состоянием, но не над диском:

| Файл                     | Отвечает за                                              |
| ------------------------ | -------------------------------------------------------- |
| `engine.ts`              | стадии сессии, переходы, вывод стадии, терминальность    |
| `task-movement.ts`       | движение ОДНОЙ задачи между вложенными стадиями цикла    |
| `action-admission.ts`    | `actions:` — что стадия разрешает делать, не уходя с неё |
| `operation-lifecycle.ts` | ход мутации: начало, вердикт, завершение                 |
| `session-facts.ts`       | проекция сессии в факты для guard-ов                     |
| `approvals.ts`           | одобрения по имени согласия                              |

Две оси не путайте: переходы отвечают «можно ли уйти отсюда», допуск действия —
«можно ли сделать это, оставаясь здесь». Коммит и правка не переходы, ребром их
не выразить.

### `session/` — состояние

`session-schema.ts` — Zod-схема сессии, единственный источник правды о её форме.
`session-store.ts` — атомарная запись через временный файл и `rename`, файловый
лок и цепочка обещаний на сессию, архивация законченных. `session-files.ts` —
правила имён и путей, включая `archive/`.

### `app/` — рантайм

`runtime.ts` вешает хуки и ведёт вызов по порядку. `mutation-orchestrator.ts`
владеет ходом мутации и резолвит движок по профилю и схеме.
`consent-orchestrator.ts` — жизненный цикл согласия. `task-api.ts` — границы
списков задач. `session-queue.ts` — сериализация операций на корневую сессию.
`profile-resolver.ts` — разворачивание `extends` в готовую схему.

### `tui/` и `dashboard/` — только чтение

Оба читают файлы сессий и ничего не решают. `parseRuntimeState` принимает уже
разобранную схемой сессию, а не текст: разбирать и защищаться от чужих форм —
работа читателя (`readSession`), а не панели.

## Путь одного вызова инструмента

**До вызова** (`tool.execute.before`), по порядку:

1. guardrails — защита от инъекций в сообщениях;
2. правила проекта (`rules/`);
3. разбор запроса согласия, если это `question`;
4. допуск задачи, если у `task` есть маркер `[workflow-task:task-N]`;
5. область записи — отказ до выполнения для `write`/`edit`/`apply_patch`;
6. действия стадии (`actions:`) — либо дефолт ядра про прямой `git`;
7. permit коммита, если вызов помечен доставкой;
8. начало хода мутации: baseline-кадр и запись операции.

**После вызова** (`tool.execute.after`): дифф против собственного кадра хода,
проверка инвариантов профиля, вердикт (`run.checks` или `session.checks`), разбор
`<workflow-result>` от агента, попытка применить переход, а при входе в конец —
запись исхода и переезд сессии в архив.

## Что чем проверяется

`mise run test` — модульные и e2e-тесты над фикстурами профилей в
`test/fixtures/profiles/`.

`mise run smoke` — прогон против **живого** OpenCode: настоящий хост во временном
каталоге и живая модель. Это отдельная интеграционная проверка hook/tool
pipeline, persistence и host behavior; её результат зависит от доступности
OpenCode и модели.

Правило проверки: **тест должен использовать форму данных, которую создаёт
production runtime.** Фикстуры TUI должны соответствовать текущей схеме сессии и
не содержать неподдерживаемых полей.
