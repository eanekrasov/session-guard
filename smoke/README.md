# host-smoke — плагин против настоящего opencode

```bash
mise run smoke                          # паритет: все canonical-сценарии через V1 и V2
mise run smoke plugin-loads create      # только эти сценарии, оба host kind
HOST_SMOKE_OPENCODE_VERSION=v1 mise run smoke create    # проверка одного хоста
bun test smoke/                         # тесты самой suite
```

Ни один сценарий не обращается к плагину напрямую. Каждый поднимает настоящий `opencode serve`
во временном проекте и проверяет то, что хост и плагин **фактически** сделали: сохранённую
плагином workflow-сессию, tool-результаты хоста, HEAD в git, файлы в проекте.

## Раскладка

`smoke/` — самостоятельный проект. Границы такие:

| Файл                       | Ответственность                                                                                                        |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `src/host/types.ts`        | локальные normalized smoke-типы: сессия, ход, tool call, durable state, plugin evidence, scenario result, parity entry |
| `src/host/transport.ts`    | внутренний seam `HostTransport` и нормализация payload-ов хоста в общие типы                                           |
| `src/host/v1-transport.ts` | transport strategy V1: HTTP API хоста                                                                                  |
| `src/host/v1-exchange.ts`  | обмен с V1-хостом вне фасада: ответы на `question` и трассировка                                                       |
| `src/host/v2-transport.ts` | transport strategy V2: сгенерированный клиент                                                                          |
| `src/host/facade.ts`       | контракт `SmokeHost`, выбор strategy, старт изолированного хоста, предел хода                                          |
| `src/registry.ts`          | один canonical registry: сценарии и определения их шагов                                                               |
| `src/runner.ts`            | один общий runner: порядок шагов, retry, assertions, cleanup, результат                                                |
| `src/parity.ts`            | сравнение V1/V2 и единый aggregate exit code                                                                           |
| `src/report.ts`            | отчёт прогона (одна схема для V1 и V2)                                                                                 |
| `src/harness.ts`           | запуск изолированного хоста, кеши, нормализация выходных payload-ов                                                    |
| `src/run.ts`               | CLI: выбор сценариев, режим паритета, коды выхода                                                                      |
| `src/v2-client.ts`         | клиент V2: сессии, промпты, формы, переключение агента                                                                 |
| `src/operator.ts`          | политика оператора: как отвечать на вопросы хоста                                                                      |
| `src/log.ts`               | вывод suite: человекочитаемо или JSONL                                                                                 |
| `test/`                    | тесты suite: registry, runner, transports, parity, report                                                              |

## Архитектура

Suite собран вокруг одного источника истины:

- **один canonical registry** (`src/registry.ts`) — сценарии и определения их шагов; все
  сценарии имеют статус `migrated`;
- **один общий runner** (`src/runner.ts`) — порядок шагов, retry-политика, assertions, cleanup и
  результат; он не знает, какой хост за фасадом;
- **один `SmokeHost`** (`src/host/facade.ts`) — контракт, которым пользуются сценарии: сессия,
  ход, durable state, проект и домашний каталог прогона, посадка сессии плагина для узких
  проверок;
- **две внутренние transport strategy** (`v1-transport.ts`, `v2-transport.ts`) — единственное
  место, где живут HTTP API V1, сгенерированный клиент V2, вопросы и формы.

Runner выбирает хост, а не список сценариев: один и тот же набор инструкций, assertions,
profile, env и files выполняется на обоих host kinds.

## Один фасад, два внутренних транспорта

Сценарий видит только `SmokeHost`: `createSession`, `runPrompt`, `readWorkflowState`,
`closeSession`, а также `workDir`, `homeDir`, `model`, `logs`, `stop`. Ни endpoints, ни
сгенерированного клиента, ни базовой аутентификации, ни форм за этой границей нет.

Транспорты приводят разное поведение хостов к одному контракту:

| Возможность         | V1                                   | V2                                                |
| ------------------- | ------------------------------------ | ------------------------------------------------- |
| промпт              | агент указывается на самом сообщении | сессия помнит агента, шаг переключает его         |
| вопросы оператора   | `question` в HTTP API                | форма, которую нужно ответить и дождаться         |
| ответ оператора     | метка варианта                       | значение формы                                    |
| shell-инструмент    | `bash`                               | `shell`                                           |
| диспатч субагента   | `task`                               | `subagent`                                        |
| патч                | `apply_patch`                        | `patch`                                           |
| аргумент пути       | `filePath`                           | `path`                                            |
| список инструментов | недоступен                           | `plugin.list` отдаёт только `{id, source, state}` |

Имена одной возможности нормализуются в одно: `shell` для команды, `task` для диспатча,
`apply_patch` для патча, а путь читается и из `filePath`, и из `path`. Иначе гарды, инварианты и
разбор вердиктов, написанные против одной возможности, молча не срабатывают на втором хосте.

## Общий контракт сценария и результат

Сценарий — это `MigratedScenarioDefinition`: `id`, `title`, `profile`, `env`, `files`, `git`,
`agent` и упорядоченные шаги. Шаг объявляет:

```ts
interface ScenarioStep {
  instruction: string;
  mutation: 'read-only' | 'mutating';
  retry: 'none' | 'poll-state' | 'same-session' | 'new-session';
  agent?: string;
  turnBudgetMs?: number;
  stateBudgetMs?: number;
  prepare?: (context: {
    workDir: string;
    sessionId: string;
    seed: (state: unknown) => Promise<void>;
  }) => Promise<void> | void;
  expect: (result: PromptResult, workspace?: StepWorkspace) => true | string;
}
```

- `agent` нужен шагу, который идёт не тем агентом, что сценарий: V1 несёт агента в сообщении, V2
  переключает агента сессии;
- `prepare` — подготовка до инструкции: файл вне разрешённого скоупа, фикстура или посадка
  сессии плагина сразу на нужную стадию. Выполняется один раз за шаг, а не на каждую попытку,
  потому что сама является мутацией;
- `turnBudgetMs` / `stateBudgetMs` — свои пределы для длинного шага;
- `expect` возвращает `true` или причину: текст попадает в evidence шага, а не в вердикт модели.

Ожидание получает `PromptResult` и `StepWorkspace`:

- `PromptResult`: нормализованный ход (`status`, `transcript`, `parts`, `toolCalls`,
  `interactions`), durable `workflowState` и `pluginEvidence`;
- `StepWorkspace`: `workDir`, `headBefore`, `headAfter` — то, чем доказывается мутация в git.

`SmokeWorkflowState` — только то, что плагин сохранил:

| Поле              | Что это                                                                   |
| ----------------- | ------------------------------------------------------------------------- |
| `status`          | состояние сессии workflow                                                 |
| `currentStage`    | стадия, на которой стоит машина                                           |
| `tasks`           | списки задач по ключу, с id и статусом                                    |
| `refs`            | durable-ссылки на документы (`refs.plan`)                                 |
| `changedFiles`    | файлы, которые ядро записало как изменённые                               |
| `runs`            | прогоны задач: задача, подстадия, статус, гейты, вердикт ядра о ходе      |
| `stageGates`      | гейты стадий по id — ими доказывается, что вердикт доехал до стадии       |
| `approvals`       | выданные согласия по типу                                                 |
| `deliveryPermit`  | есть ли разрешение на поставку                                            |
| `deliveryReceipt` | квитанция о поставке: непустая строка доказывает, что поставка состоялась |
| `durableMutation` | применена ли мутация                                                      |

Вердикт строится на этих фактах, а не на тексте ответа. Предпочтение отдаётся durable state,
нормализованным tool calls и структурированному результату; текст отказа читается только там, где
структурированного сигнала нет, и это отмечено в самом шаге как документированный fallback.

Результат сценария строго один из трёх:

| Статус    | Что означает                                                                                                        |
| --------- | ------------------------------------------------------------------------------------------------------------------- |
| `pass`    | каждый шаг выполнил своё ожидание на наблюдаемом свидетельстве                                                      |
| `fail`    | непройденное ожидание, инфраструктурное исключение или ошибка плагина                                               |
| `blocked` | подтверждённое ограничение контракта V1/V2, недоступная обязательная возможность или недоказуемый результат мутации |

`blocked` создаёт только runner или facade, и только с `blockedReason` из закрытого набора
(`adapter_contract_mismatch`, `required_host_capability_unavailable`, `indeterminate_mutation`) и
с evidence, где названы operation, host kind, шаг и наблюдаемое ограничение.

`not-run` — **не** статус результата сценария. Он живёт только в `ParityReportEntry.parity` и
всегда имеет причину:

- `pending-migration` — сценарий ещё не мигрирован (aggregate exit code `4`);
- `live-environment-unavailable` — migrated обязательный сценарий не удалось запустить до его
  начала: нет бинарника хоста, модель не разрешается, хост не поднялся (aggregate exit code `5`).

Ошибка bootstrap, вызванная сломанным harness или плагином (не читается конфигурация, нет
фикстуры профиля, не собрался плагин), остаётся фатальной и завершает прогон кодом `2` — в фасаде
это одно место, `classifyBootstrapError`. Ошибка внутри уже поднятого хоста (транспорт, tool,
assertion) — это `fail` сценария, а не `blocked` и не `not-run`.

Aggregate exit code один для обоих host kind:

| Код | Условие                                                                                     |
| --- | ------------------------------------------------------------------------------------------- |
| `0` | все обязательные runnable-сценарии прошли и незавершённого нет                              |
| `1` | есть `fail`                                                                                 |
| `2` | ни один сценарий не запустился и причина не названа, либо фатальная ошибка адаптера/запуска |
| `3` | есть `blocked` и нет `fail`                                                                 |
| `4` | осталась только незавершённая миграция                                                      |
| `5` | живая среда недоступна для migrated-сценария                                                |

Приоритет: `fail`/fatal, затем `blocked`, затем недоступная среда, затем незавершённая миграция.
Причина `not-run` читается **до** вывода «ничего не запускалось»: выбор из одних
`pending-migration` — это `4`, а хост, который не поднялся, — `5`; ни то, ни другое не «нет
runnable-сценария».

### Паритет

- **structural parity** — один canonical registry, одинаковые metadata, инструкции, assertions,
  profile, env и files для V1 и V2;
- **behavioral parity** — одинаковый ожидаемый результат на обоих host kinds.

Паритетная таблица отчёта — `scenario | V1 | V2 | parity | evidence`, одна строка на каждый
выбранный canonical-сценарий, в любом режиме. `—` в колонке хоста означает, что эта сторона не
дала результата, а причина названа в колонке `parity` и в доказательстве.

| parity    | Когда                                                                                                                          | Exit code                                |
| --------- | ------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------- |
| `pass`    | обе стороны `pass` — одинаковая ожидаемая семантика                                                                            | не влияет                                |
| `limited` | полного behavioral parity нет: одна сторона `blocked`, обе ограничены одинаково, или в прогоне измерялся только один host kind | не влияет (`blocked` считается отдельно) |
| `fail`    | стороны ведут себя по-разному или хотя бы одна сторона `fail`                                                                  | `1`                                      |
| `not-run` | сценарий не мигрирован (`pending-migration`) или сторона не запустилась (`live-environment-unavailable`)                       | `4` / `5`                                |

`blocked` никогда не считается `pass`. Сценарий с недоступной стороной не исчезает из таблицы:
результат работавшей стороны остаётся в своей колонке, а строка получает `not-run` с причиной.
Матрица `scenario | required on V1 | required on V2 | expected status | reason` строится из
canonical registry, а не из ручной таблицы: каждый canonical-сценарий обязателен на обоих host
kinds. `not-run`-строки этой таблицы — вход `aggregateExitCode`, поэтому отчёт и код выхода не
могут расходиться. Отчёт пишется в `docs/plans/host-smoke.md`.

## Как выбрать V1/V2

| Команда                          | Что запускается                                                                                                    |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `mise run smoke`                 | parity-прогон: canonical-сценарии через V1 **и** V2 один за другим, одна parity-таблица                            |
| `HOST_SMOKE_OPENCODE_VERSION=v1` | проверка одного хоста: только V1; строка паритета получает `limited` — вторая сторона в этом прогоне не измерялась |
| `HOST_SMOKE_OPENCODE_VERSION=v2` | то же для V2                                                                                                       |

Бинарники: по умолчанию `/opt/homebrew/Cellar/opencode/1.18.32/bin/opencode` (V1) и
`/opt/homebrew/Cellar/opencode-v2/2.0.16/bin/opencode` (V2); переопределяются
`HOST_SMOKE_V1_BINARY` и `HOST_SMOKE_V2_BINARY`. Если явно выбранный хост не отвечает ожидаемому
контракту, запуск завершается понятной ошибкой этого адаптера — подмены V1 на V2 (или наоборот)
нет. Поддерживаются ровно эти две версии; других, неизвестных или будущих версий OpenCode suite
не обещает.

## Что доказывает каждый сценарий

| Сценарий          | Что проверяется                                                                          |
| ----------------- | ---------------------------------------------------------------------------------------- |
| `plugin-loads`    | хост загрузил плагин и вызвал его инструмент, получив структурированный результат        |
| `no-session`      | без workflow-сессии плагин не вмешивается: ровно одна команда, durable state отсутствует |
| `create`          | сессия сохранена и находится на первой стадии схемы                                      |
| `git-block`       | прямой `git commit` отклонён: HEAD не сдвинулся, разрешения и квитанции нет              |
| `task-control`    | worker не смог изменить статус задачи: durable-статус остался `pending`                  |
| `commit-gate`     | ранняя поставка отклонена: HEAD не сдвинулся, разрешения и квитанции нет                 |
| `plan-consent`    | согласие прошло через фасад и записано в `refs.plan`, стадия ушла из `planning`          |
| `commit-cwd`      | HEAD сдвинулся, квитанция записана и равна новому HEAD                                   |
| `commit-mismatch` | HEAD сдвинулся, но квитанции нет, а выданное разрешение больше не действует              |
| `cicd-full-cycle` | весь pipeline: стадии, гейты, тестовые задачи, согласие `deploy`, финальная стадия       |
| `workflow-result` | вердикт субагента доезжает до гейта стадии                                               |
| `verify-loop`     | два вердикта закрывают гейты прогона и переводят задачу на следующую стадию              |

### Порядок доказательства для сценариев поставки

`commit-gate`, `commit-cwd` и `commit-mismatch` работают с настоящей мутацией git, поэтому все
факты, которые можно, читаются из состояния:

1. `deliveryReceipt` — записана ли квитанция, и совпадает ли она с новым HEAD;
2. `deliveryPermit` — выдано ли разрешение и перестало ли оно действовать;
3. `headBefore` / `headAfter` — сдвинулся ли HEAD;
4. нормализованный вызов команды — та ли команда выполнялась;
5. структурированный маркер отказа, затем статус вызова: `completed` без отказа — это `fail`
   («команда выполнилась, хотя должна была быть отклонена»);
6. текст отказа — только документированный fallback для хоста, который не сообщил ни маркера, ни
   ошибки.

Каждый `pass` печатает эти наблюдения в evidence, а не пересказ модели:

```text
commit-cwd      delivery=receipt:cb28b9c6…;  head=1ec7dbff→cb28b9c6; files=["src/smoke-1.ts"]
commit-mismatch stage=commit; delivery=none;  head=dd9b8ccc→a047d3d9; files=["src/smoke-1.ts"]
commit-gate     delivery=none;               head=5ff236fb→5ff236fb; files=[]
```

### Pipeline

`cicd-full-cycle` идёт по профилю `cicd` одним сценарием: создание сессии → согласие `plan` →
setup (`checkout_done`) → build (`build_done`) → список `test_suite` → unit → integration →
deploy (`deploy_done`) → согласие `deploy` → smoke (`smoke_result`) → стадия `done`.

Две детали, на которые опирается доказательство:

- файлы проверяются **на диске**: диспатчи pipeline описываются как `[workflow-task:checkout]`, а
  запись изменений ядро ведёт только для `[workflow-task:task-N]`;
- вердикт принимается только из **финального сообщения субагента**: процитированный оркестратором
  тег вердиктом не является.

### `workflow-result`

Узкая проверка одного механизма: сессия плагина сажается прямо на стадию, объявляющую гейт
`review`, и сценарий доказывает ровно один durable факт — что `<workflow-result>` субагента
записан гейтом. Один шаг вместо двадцати минут pipeline: так проверяется механизм, а не путь до
стадии, и регрессия в этой связке ловится за минуту.

## Retry и таймауты

Стратегия повтора — решение реестра, а не runner-а, и она зафиксирована тестом:

- `same-session` разрешён только для шага, который явно `read-only`: повтор мутации запрещён;
- `poll-state` отправляет инструкцию **один раз**, дальше runner читает durable store до бюджета
  и не повторяет инструкцию;
- `none` — ровно одна попытка (шаги поставки: команда меняет git, повтор после таймаута мог бы
  выполнить её по-настоящему);
- `new-session` в текущей реализации не поддерживается, и объявить его в реестре нельзя.

Правила обработки исхода:

- mutating-инструкция **никогда** не повторяется в той же stateful-сессии: если ожидание не
  выполнено, runner читает durable исход через фасад;
- промпт, оборвавшийся исключением, — та же ситуация для мутации: неизвестно, дошла ли
  инструкция. Если состояние подтверждает ожидание шага — это `pass` с пометкой в evidence, что
  промпт не вернулся, а исход доказан сохранённым состоянием; если состояние недоступно или
  ожидание не подтверждает — `blocked` с `indeterminate_mutation`;
- обычный `fail` остаётся только для доказанного случая: ход завершился, ожидание не выполнено и
  сохранённого изменения нет;
- ход, вышедший за бюджет, не является вердиктом: он сообщается в evidence как `timed-out`, а шаг
  судится по durable state, который сохранил плагин;
- `blocked` не может скрыть провал: если исход доказуем, он доказывается, а не заменяется
  «неопределённостью».

Бюджеты: у шага может быть свой `turnBudgetMs` (длинный шаг pipeline законно идёт минутами) и свой
`stateBudgetMs` (сколько ждать подтверждения из состояния). Общий предел хода применяется в фасаде
ко **всему** ходу, а не к отдельному вызову хоста: стратегия V2 ограничивает каждый свой вызов
отдельно, и залипший вызов между ними иначе не ограничивался бы ничем.

## Изоляция

`XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME` и `XDG_CACHE_HOME` указывают на временное
дерево, поэтому ваши агенты, плагины, MCP-серверы и сессии в прогоне не участвуют. Из окружения
заимствуются две вещи — без них не будет живой модели: совпадающие записи из `provider`/`providers`
вашего конфига opencode и `auth.json`. `HOST_SMOKE_MODEL` (или `model` верхнего уровня в конфиге)
определяет, какие имя провайдера и id модели останутся; остальные провайдеры удаляются.

Из окружения оператора не наследуются `OPENCODE_*` и `OPENCHAMBER_*`: иначе изолированный хост
читал бы чужой конфиг, ставил бы из npm чужие плагины и загружал бы их в прогон.

Проект, в котором работает хост, — свежий git-репозиторий с профилем сценария, `commit-task.ts` и
файлом плана. По окончании прогона он удаляется.

Кеш — это кеш: каталог зависимостей хоста и npm-кеш живут вне временного дерева, иначе каждый
старт скачивал бы их заново. Сессии, состояние и конфигурация при этом остаются одноразовыми.

## Модель — часть теста

Живая модель сама решает, вызывать ли инструмент, который её просили вызвать, поэтому шаг может
упасть из-за модели, а не из-за плагина. Read-only шаг повторяется (`HOST_SMOKE_ATTEMPTS`, по
умолчанию 3), mutating — нет. **Шаг, которому понадобились повторы, — проблема промпта; шаг, не
прошедший ни разу, — находка.** Фиксированная длительность не является порогом pass/fail.

Поэтому `fail` несёт `failureKind`, вычисленный по тому, что увидел адаптер:

| failureKind | Что наблюдалось                                                                   | Как читать                                             |
| ----------- | --------------------------------------------------------------------------------- | ------------------------------------------------------ |
| `model`     | ни одного завершённого вызова инструмента плагина: инструкция не дошла до плагина | поведение host/plugin не наблюдалось, прогон повторить |
| `host`      | вызов инструмента плагина завершился, а ожидание всё равно не выполнено           | может быть дефектом контракта — это уже `parity: fail` |
| `unknown`   | инструмент вызывался, но ни один вызов не завершился; либо необработанная ошибка  | решает транскрипт, прогон повторить                    |

`failureKind` есть только у `fail`; `blocked` и `pass` его не несут, и это проверяется инвариантом
результата. Одна неудачная попытка из-за живой модели не подтверждает дефект реализации: evidence
фактического вызова сохраняется, состояние читается, прогон повторяется — и только если результат
остаётся неопределённым, фиксируется, что поведенческий паритет не подтверждён.

## Окружение

| Переменная                     | Значение                                                     |
| ------------------------------ | ------------------------------------------------------------ |
| `HOST_SMOKE_MODEL`             | id модели; по умолчанию `model` из вашего конфига opencode   |
| `HOST_SMOKE_PLUGIN`            | не собирать, а загрузить этот путь вместо `dist`             |
| `HOST_SMOKE_ATTEMPTS`          | число попыток read-only шага, по умолчанию 3                 |
| `HOST_SMOKE_PROMPT_TIMEOUT_MS` | предел на весь ход, по умолчанию 120000                      |
| `HOST_SMOKE_STATE_POLL_MS`     | как часто читать состояние при `poll-state`                  |
| `HOST_SMOKE_OPENCODE_VERSION`  | `v1` или `v2`: сузить прогон до одного host kind             |
| `HOST_SMOKE_V1_BINARY`         | путь к бинарнику V1                                          |
| `HOST_SMOKE_V2_BINARY`         | путь к бинарнику V2                                          |
| `HOST_SMOKE_LOG_LEVEL`         | уровень логов suite                                          |
| `HOST_SMOKE_HOST_LOG_LEVEL`    | уровень логов самого хоста; `debug` дублирует его в вывод    |
| `HOST_SMOKE_LOG_LEVEL=debug`   | включить диагностические события, вопросы и обмен USER/MODEL |
| `HOST_SMOKE_OUTPUT`            | `human` (по умолчанию) или `jsonl`                           |
| `FORCE_COLOR=1`                | форсировать цвета, когда stderr не подключён к TTY           |
| `NO_COLOR=1`                   | отключить цвета                                              |

Для машинно-читаемого вывода используйте JSONL в stderr:

```bash
HOST_SMOKE_OUTPUT=jsonl HOST_SMOKE_LOG_LEVEL=debug mise run smoke 2>host-smoke.jsonl
```

Каждая строка — одно событие с `timestamp`, `type`, `message` и полями, специфичными для события,
например `scenario`, `hostKind`, `attempts` и `durationMs`. В человекочитаемом режиме логи,
доказательства и отчёт выводятся по-русски; при `HOST_SMOKE_OUTPUT=jsonl` переводится только
человекочитаемый текст, а имена событий и ключи JSON остаются английскими.

## Границы импортов

`smoke/` — внешний потребитель собранного плагина. Он **не** импортирует ни исходники, ни типы
production plugin из `src/`, `dist/` или внутренних модулей, включая `import type`: обратная
compile-time зависимость сделала бы сценарий зелёным из-за совпадения типов, а не из-за поведения
собранного артефакта. За этим следит `no-restricted-imports` в `eslint.config.js`.

Всё, что нужно сценариям, объявлено локально в `smoke/src/host/types.ts`; внешний JSON сужается
вручную. Обратной зависимости от production plugin нет: весь его контракт, который нужен
сценариям, выражен через фасад и normalized observations.

## Что suite знает про хост

Наблюдаемые свойства, на которые опирается suite:

- плагин загружается из `file://` **каталога** (`file://…/dist`) — именно так его прописывает
  оператор в своём конфиге. Упакованный `.tgz` за `file://` **не** загружается;
- хост читает список агентов один раз, при старте, поэтому агенты профиля должны быть на месте до
  подъёма сервера;
- инструмент `question` — весь путь согласия — регистрируется только для интерактивных клиентов,
  если не задан `OPENCODE_ENABLE_QUESTION_TOOL`, и по умолчанию запрещён без
  `permission: { question: "allow" }`;
- `ToolContext.agent` несёт имя вызывающего агента — именно против него работает ограничение
  редактирующих агентов;
- V2 игнорирует унаследованный `OPENCODE_SERVER_PASSWORD`, генерирует собственные учётные данные и
  требует их при каждом вызове `/api`;
- V1 отдаёт результат хода по частям: ответ на `POST /session/:id/message` содержит только
  последнее сообщение хода, а tool-part лежит в предыдущем assistant-сообщении, которое видно
  через `GET /session/:id/message`;
- V2 исполняет plugin tools через свою обёртку (`execute`) и сообщает, какие именно плагинные
  tool-ы выполнились, в `state.metadata.toolCalls`;
- V2 ограничивает каждый свой вызов отдельно, поэтому общий предел нужен на уровне хода;
- вердикт субагента принимается только из его собственного финального сообщения.
